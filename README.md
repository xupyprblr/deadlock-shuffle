# Deadlock Shuffle

Рандомайзер для Deadlock по мотивам dota2random.info: случайный герой, сборка из 12 предметов с порядком покупки, порядок прокачки способностей и оценка затара по статистике. Данные по героям, предметам и иконкам обновляются сами, без ручной правки.

## Что умеет

- **Герой** — из списка играбельных героев (выключенные и находящиеся в разработке отсекаются автоматически). Фильтр по классам (убийца, боец, стрелок, мистик) и исключение конкретных героев.
- **Затар** — 12 универсальных слотов. «Баланс инвеста» (под героем): Хаос, Поровну, Все в один. Выбор тиров I–IV и лимит активных предметов. Тир V (легендарки) не участвует: в игре он выпадает только в спецрежиме и случайно.
- **Механика компонентов** — улучшение в Deadlock «съедает» свой компонент, поэтому предмет и его компонент (в том числе через цепочку, например Sprint Boots → Enduring Speed) вместе не выпадают никогда.
- **Запреты для героев** — некоторые предметы герою не продаются (у Deadman Danny и Graves нет хедшот-предметов, у героев без зарядов нет Extra Charge / Rapid Recharge / Recharging Rush и т. п.). В API игры этих данных нет, поэтому `sync.mjs` определяет их по статистике покупок за 30 дней: предмет с нулём покупок при ожидаемых 200+ считается запрещённым. Сейчас найдено 45 пар герой/предмет у 16 героев. Кнопка «Другой герой» подбирает только того, кто может купить текущую сборку.
- **Порядок прокачки** — 16 шагов: у каждой из 4 способностей открытие и 3 улучшения, с подсказками по каждому улучшению.
- Кнопки по группам: «Крутить»; «Перекрутить» — героя / предметы (герой остаётся); «Забрать» — в игру / ссылка. Замена одного предмета — клик по плитке.
- Ссылка на конкретный результат (`?b=…`) — работает и после обновления данных, потому что хранит id, а не сид.
- RU / EN, пробел — крутить.

## Как устроено автообновление

Источник — открытый [Deadlock API](https://deadlock-api.com) (`api.deadlock-api.com/v1/assets/*`, CORS открыт).

Два уровня, чтобы сайт не зависел ни от одного из них:

1. **Сервер (cron).** `scripts/sync.mjs` раз в 3 часа (GitHub Actions) скачивает героев, предметы, способности, линии и номер патча, нормализует в компактные `public/data/ru.json` и `en.json` (~150–200 КБ) и зеркалит иконки в `public/icons` (~8 МБ). Если хэш данных не изменился, коммита нет.
2. **Браузер (на лету).** При открытии страницы `app.js` запрашивает `/v1/assets/client-versions` (4 КБ). Если версия игры новее, чем в снимке, браузер сам собирает свежий снимок тем же кодом нормализации (`public/js/normalize.js`) и кэширует его на 6 часов. Способности нового героя подгружаются отдельно по его id.

Если API недоступен, сайт работает на последнем снимке.

## Порядок покупки

Переключатель под героем. Слоты нумеруются как в игре: сверху вниз, затем следующий столбец (на телефоне — 3 столбца по 4 слота).

- **Полный рандом** — порядок покупки случайный, предмет IV тира может быть первым.
- **Псевдо-рандом** — случайный, но шанс оказаться следующим обратно пропорционален цене: дешёвые обычно раньше, дорогие изредка проскакивают вперёд.
- **По фазам** — 3 фазы по 4 предмета: ранняя игра (тиры I–II), середина (II–III), поздняя (III–IV); внутри — по возрастанию цены. Номера слотов и подписи фаз окрашены по фазам.

Порядок покупки фиксирован для каждой крутки: первый показанный порядок запоминается, а для остальных режимов выводится из сида крутки. Сколько ни переключай режимы (и даже язык), каждый режим показывает один и тот же порядок — перебором «подобрать получше» нельзя. Новый порядок — только с новой круткой. Тиры фаз строго соблюдаются, когда «По фазам» выбран до крутки.

## Перенос сборки в игру (без модов)

Кнопка **«В игру»** копирует код сборки. В Deadlock: **Сборки → Создать новую → кнопка вставки** — предметы встают по порядку покупки, порядок прокачки заполняется сам. В режиме «По фазам» разделы называются системными ключами игры (`#Citadel_HeroBuilds_EarlyGame` / `MidGame` / `LateGame`), поэтому игра подписывает их на языке игрока («Ранний этап», «Середина матча», «Поздний этап»). В описание сборки попадают оценка затара и ссылка на крутку.

Формат кода — `base64(zstd(protobuf))`, Valve его не документирует. Схема полей — из открытого проекта [Deadlock Browser Build Maker](https://github.com/JoniSmiff/Deadlock-Browser-Build-Maker) (MIT). Наш кодировщик (`public/js/buildcode.js`) на 300 сборках выдаёт байт-в-байт тот же код, что эталонный, а эталонный декодер с настоящим zstd читает все наши коды. Если Valve поменяет формат, кнопка перестанет работать — тогда сверить схему с обновлённым эталоном.

## Технический раздел «Сборки игроков» (не входит в релиз 1)

`public/lab/builds.html` — скрытая страница: с главной ссылок нет, стоит `noindex`. На сайте: https://randomlock.com/lab/builds.html

- **По герою:** опубликованные сборки игроков со статистикой — матчи, игроки, винрейт, 95% интервал (Уилсон), отклонение от винрейта героя; фильтры: период 7/14/30/90 дней, ранг, минимум матчей, сортировка.
- **По ID:** одна или несколько сборок по ID → карточка в стиле игрового окна сборок (разделы, плитки предметов по тиру и категории, сетка «Порядок улучшения умений»), матчи, игроки и винрейт за 14 дней и за всё время, строка «на сколько винрейт выше/ниже среднего по герою», кнопка «В игру». Клик по ID копирует его. Содержимое карточки берётся прямо из игры (`/v1/builds/{hero}/{id}?force_refetch=true`, лимит 20/мин с IP, кэш на час): база API обновляет сборки с опозданием, иногда на месяцы. При ошибке — версия из базы. Ссылка `?ids=…`.
- **Сравнение:** сборки попадают сюда только кнопкой «Добавить в сравнение» (в таблице героя — «+ Сравнить»), до 6 штук; список хранится в браузере, ссылка `?cmp=…`. В карточке — «Убрать из сравнения». «Открыть» в таблице героя показывает сборку в окне и в сравнение не добавляет.
- Данные запрашиваются из браузера напрямую в Deadlock API (`/v1/analytics/hero-build-stats/{hero}`, `/v1/builds`, `/v1/analytics/hero-stats`), лимит API — 200 запросов в минуту с IP.
- **Аномалии и самородки** (фильтр «Показать»): поиск непопулярных сборок с высоким винрейтом.
  - Кандидат: не в топ-10% сборок героя по матчам, ≥ 50 матчей, ≥ 10 разных игроков.
  - «Аномалия»: WR ≥ 55% и нижняя граница одностороннего 95% интервала Уилсона выше винрейта героя; «Самородок»: то же с WR ≥ 60%.
  - «Оценка» — эмпирический байес: WR поджимается к винрейту героя с весом 275 матчей (настоящий разброс между сборками ≈ 3 п.п.); в этом режиме сортировка по ней.
  - Почему не голый порог: у сборок до 50 матчей разброс винрейта почти целиком шум — из 1313 таких сборок у 313 «60%+».
- Экономия лимита API (аналитика: 200 запросов/мин с IP, 2000/мин глобально на всех пользователей API):
  - начало периода в запросах округляется до часа — у всех зрителей одинаковые адреса, ответы отдаёт кэш Cloudflare и часовой кэш API, лимит не тратится;
  - ответы хранятся в браузере час (localStorage, префикс `lab:api:`) — повторный просмотр не делает запросов;
  - на `429` / `503` страница ждёт, сколько просит `Retry-After` (не больше 60 с), и повторяет до 4 раз.
- Оговорки: засчитывается сборка, выбранная в начале матча; статистика суммирует все версии сборки; учтены только матчи с разбором записи; на малых выборках огромная погрешность.
- **При сборке коммерческого релиза исключить** `public/lab/`, `public/js/lab.js`, `public/css/lab.css`.

## Оценка затара

Под сборкой — вердикт (Мета-затар / Рабочая сборка / Рискованно / Челлендж / Чистый троллинг) и примерный шанс на победу.

- Сырой винрейт предмета смещён: дорогие и поздние предметы покупают те, кто уже выигрывает (корреляция винрейта с минутой покупки 0,40). Поэтому каждый предмет сравнивается с предметами **того же тира на этом же герое** — после этого корреляция падает до 0,08.
- `sync.mjs` раз в сутки пишет `public/data/stats.json`: базовый винрейт героя и дельту каждого предмета (статистика всех рангов за 30 дней, предметы с 300+ покупками).
- Шанс на победу = 50% + средняя дельта предметов сборки (шанс затара при среднем герое; сила самого героя не добавляется, чтобы процент и вердикт всегда росли вместе). Это ориентир, а не прогноз: синергия предметов и игра команды не учитываются.
- Пороги вердиктов откалиброваны по 20 000 случайным сборкам (`scripts/calibrate.mjs`): верхние ~10% — «Мета-затар», нижние ~10% — «Чистый троллинг».
- У совсем новых героев оценки нет, пока не наберётся статистика.

## Активные предметы

В игре максимум 4 активных слота. По умолчанию число активок в сборке каждую крутку случайно от 0 до 4; ползунок в настройках фиксирует точное число. Замена одного предмета сохраняет тип слота.

## Новые герои — автоматически

- `scripts/watch.mjs` — быстрый сторож. Делает два лёгких запроса: версия клиента и список активных героев. Сравнивает их с `public/data/meta.json` и печатает `CHANGED`, если вышел патч или изменился состав героев. В GitHub Actions запускается каждые 20 минут и только тогда включает полную синхронизацию и деплой.
- `public/data/roster.json` — журнал героев с датой первого появления (`firstSeen`). Новых героев `sync.mjs` пишет в лог (`НОВЫЕ ГЕРОИ: …`), в сводку CI и в сообщение коммита.
- На сайте герой с `firstSeen` младше 30 дней получает бейдж «Новинка» — на постере и в пуле, как на экране выбора в игре.
- Герой считается вышедшим, когда в API `player_selectable = true`, `disabled = false` и `development_state = release`. Флаг `in_development` не используем: у свежих героев он остаётся `true` и после релиза.
- Запреты на предметы для нового героя появляются только когда у него наберётся статистика (≥ 5000 матчей у самого популярного предмета), чтобы в первые дни не было ложных запретов.
- Если сайт хостится без CI, хватит и браузера: при выходе патча он сам пересобирает данные и помечает незнакомых героев «Новинкой».

## Структура

```
public/
  index.html          страница
  css/styles.css
  js/app.js           интерфейс
  js/random.js        вся логика рандома (чистые функции)
  js/buildcode.js     код сборки для импорта в игру
  js/lab.js           технический раздел «Сборки игроков» (не в релизе 1)
  lab/builds.html     страница технического раздела
  js/normalize.js     API → компактный JSON (общий для Node и браузера)
  data/{ru,en}.json   снимки данных
  icons/              зеркало иконок
scripts/
  sync.mjs            синхронизация (флаги: --icons, --langs ru,en)
  watch.mjs           быстрый сторож: патч / новые герои
  calibrate.mjs       калибровка порогов оценки затара
  build-demo.mjs      демо одним файлом
  test.mjs            2000 роллов с проверкой всех правил
  build-demo.mjs      одностраничная демка со встроенными данными
.github/workflows/sync.yml
```

## Запуск

Нужен Node 18+, зависимостей нет.

```bash
npm run sync:icons   # скачать данные и иконки
npm test             # проверить логику
npm run dev          # http://localhost:5173
```

## Хостинг

Сайт полностью статический: подойдёт GitHub Pages (workflow уже настроен), Cloudflare Pages, Netlify или любой nginx.

**GitHub Pages (текущий хостинг):** https://randomlock.com (домен на Porkbun; старый адрес https://xupyprblr.github.io/deadlock-shuffle/ перенаправляет туда) — в Settings → Pages источник «GitHub Actions», Custom domain `randomlock.com`, Enforce HTTPS. Файл `CNAME` не нужен: при публикации через Actions домен берётся из настроек. Все пути в коде относительные, поэтому сайт работает и в подпапке, и в корне домена.

DNS на Porkbun: `A` для корня → 185.199.108.153, 185.199.109.153, 185.199.110.153, 185.199.111.153; `AAAA` → 2606:50c0:8000::153, 2606:50c0:8001::153, 2606:50c0:8002::153, 2606:50c0:8003::153; `CNAME www` → `xupyprblr.github.io`; `TXT _github-pages-challenge-xupyprblr` — код подтверждения домена из настроек аккаунта GitHub. Workflow публикует сайт при пуше в main, при изменении данных (сторож каждые 20 минут) и раз в 3 часа.

**Свой сервер:** положить `public/` в корень сайта и добавить в crontab:

```
17 */3 * * * cd /var/www/deadlock-shuffle && node scripts/sync.mjs --icons >> sync.log 2>&1
```

## Терминология

Категории на русском — как в игре: **Оружие, Спиритизм, Живучесть** (в этом порядке). Имена героев, предметов и способностей — на английском.

Картинки предметов берутся из поля `shop_image` (актуальные иллюстрации магазина). Поле `image` в API содержит старые плоские иконки и используется только как запасной вариант.

## Что стоит проверить в игре

- Число слотов в сборке по умолчанию — 12. Если в текущем патче другое количество, поменяйте `slots` в `DEFAULTS` в `public/js/random.js`.
